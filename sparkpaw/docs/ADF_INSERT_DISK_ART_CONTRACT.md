# ADF INSERT DISK status art contract

The user approved the complete-line INSERT DISK 3 art and then played
`dist/Campaign-ADF-Disk3-Type` through the complete three-disk campaign in
FS-UAE, including START AT and disk swaps. The procedure below is now the
accepted Disk 3 construction route. Real A1200/physical floppy remains
untested; earlier rejected-art notes below are historical.

## Mandatory route for every future disk number

1. Use the accepted `sparkpaw-insert-disk-type-v1.png` typography sheet as the
   visual source. Create a **complete** `INSERT DISK N` line in that style and
   save its lossless source PNG under `assets/concept/`. Record its source,
   prompt or construction method, hash and review status in
   `docs/IMAGEGEN_PROMPTS.md` or the relevant art log.
2. Add the new full-line source and crop to `TYPE_SOURCES` in
   `tools/generate_disk_status.py`. Generate the native strip with `make_patch`:
   216x24 line, inset (4,6) in 224x40, unchanged loading palette and floppy
   image. Do not paste, scale or draw a digit separately in the packager.
3. Extend the package's `PATCHES` inventory and copy the generated strip to
   every disk that may display its request. Check dependencies per disk.
4. Extend `tests/test_disk3_status_consistency.py` (or its successor) to pin
   the approved 1/2 strips, the new source, shared dimensions, palette and
   inset. Build a side-by-side native preview of 1/2/N and inspect it before
   staging. The user's visual approval of each new number is a separate gate
   from ADF file readback and FS-UAE gameplay.

The oversized pasted 3 and two code-drawn replacements were rejected. Do not
reuse those construction paths for future numbers.

The user approved the existing INSERT DISK 1 and INSERT DISK 2 presentation.
The first three-disk campaign test loaded Drowned correctly, but the numeral

The status art must use the shared loading image, its 64-colour palette, and
one 224x40 status strip positioned at (48,192). The source for digits 1/2 is
`assets/concept/sparkpaw-insert-disk-type-v1.png`, converted by
`tools/generate_disk_status.py`. The approved SPBM strip hashes are:

- Disk 1: `4f5f8df0da68e02412f315093d57d14746a77791bf99b658d6734424542044fd`
- Disk 2: `c7bacacd27513d0767d627d4bb02064d47ca54d2b08672093e60bc25805dd543`

The 1/2 source is a generated raster typography sheet, **not a runtime font**.
The generator crops each complete line from the sheet, resizes it to 216x24,
quantizes it to the loading palette and places it at (4,6) in the strip. It
does not render individual characters at runtime.

Disk 3 now follows that same full-line process using
`assets/concept/sparkpaw-insert-disk-type-v2-disk3.png`, generated by editing
the 1/2 source as a reference. `tools/generate_disk_status.py` owns all three
source bands and creates all three SPBM strips. The new source's SHA-256 is
`846d5e5959eb75878fc3223e52d5a4fbc54297f756df1be5216dd9041de260b2`.
`tools/package_campaign_drowned_adf.py` copies these three generated strips;
it must never paste a separate numeral onto an existing strip. The rejected
separate digit and code-drawn glyph remain historical evidence only.

Run `../.venv/bin/python3 tests/test_disk3_status_consistency.py` after every
art/package change. It pins the approved 1/2 SPBM hashes and the third source,
checks the shared palette/geometry/inset, and compares the saved Disk 3 SPBM
with a fresh conversion from the full-line source. The packager also decodes
every packed asset and reads every file back from each ADF. The current visual
comparison preview is `build/multidisk-probe/status/preview-2x.png`.
