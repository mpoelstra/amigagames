SPARKPAW AGA RENDER BENCHMARK
=============================

rb21 calibrated 4+3 versus 4+4 production-worst-case proof
-----------------------------------------------------------

Run `Sparkpaw-Renderbench-4plus3`, exit with left mouse, and preserve its
`renderbench.log`. Rename that log before running `Sparkpaw-Renderbench-4plus4`,
which otherwise writes to the same filename. Keep both RAW files beside both
executables.

The binaries differ only in rear depth and corresponding BPLCON0/pointer setup.
Both use the same scene, scrolling, six 48-line sprite DMA channels, line-252
HUD switch and synchronized line-253 production ordering. The workload is the
current runtime worst case: two 64x64 Striders plus two 32x24 beetles, all eight
projectiles, the measured maximum nine camera-visible diamonds, splash, and the
every-other-frame update of water in both clean and display buffers.

Both logs must report the same build ID and `result=WITHIN_FRAME`:

```text
2026-08-14-rb21-calibrated-production-worst-case
matched_load=sprites6x48 hud_line=252 bobs_line=253 enemies=2x64x64+2x32x24 projectiles=8x16x9 collectibles=9x16x21 splash=32x16 water_targets=2
over_budget_frames=0 result=WITHIN_FRAME
```

Compare `work_max_elapsed_lines`; subtract it from 59 (PAL lines 253..311) for
the remaining line budget. A 4+4 result within the frame is necessary but not
sufficient for integration; the 4+3 difference measures eighth-plane DMA cost.
Return both logs and a smoothness/corruption report. This remains an isolated
test, not production, ADF or real-hardware verification.

rb19c REAR16 4+4 visual proof (accepted)
-----------------------------------------

The preceding rb19c isolated benchmark changes its rear bitmap only from three
to four planes and displays the exact Phase 6B.6 REAR16 art. Supplied FS-UAE
evidence accepts its colour benefit and stable scrolling as a visual proof, not
as a production timing result.

The rear proof adds 22,528 bytes to this 672x256 test bitmap because
`AllocBitMap` measures 88 bytes per row. A production
2048x256 rear would add exactly 65,536 Chip bytes; the planned 3072px rear would
add 98,304. Raster fetch rises from seven to eight planes (+14.3%). Run from the
Sparkpaw drawer with both RAW files beside the executable. Review
whether cyan/green ruin materials, forest separation and mountain/cloud ramps
are a clearly worthwhile improvement over alpha.7 REAR8. Exit with left mouse
or wait for the frame limit, then return `renderbench.log`. It must report:

```text
2026-08-14-rb19c-bank0-color00-31
bitmap=672x256 depth=4+4
rear16_loaded=1 source=672x256x4
overflow=0
```

Do not infer production 50 Hz safety from this lightweight proof. A positive
visual result permits the next matched workload benchmark with the line-252 HUD
switch and line-253 Bob pass; a weak visual result rejects the extra plane.

Experimental branch note (rb15)
-------------------------------

The `codex/sparkpaw-aga-4plus3-renderbench` branch changes only this isolated
benchmark from the accepted 3+3 layout to an AGA-native 4+3 dual playfield.
PF1 uses four odd-numbered bitplanes and pens 0-15; PF2 uses three even-numbered
bitplanes and AGA `PF2OF=16` so its pens live at 16-23. Bright magenta foreground
platforms prove that PF1 bitplane four is fetched. Rear geometry must retain its
independent quarter-speed scroll and separate blue palette.

This is not the game executable and does not contain the player, Strider, HUD or
gameplay. The first rb14 build overflowed its inherited 128-word Copper buffer
after adding the seventh pointer and AGA palette passes; Exec reported corrupt
memory during cleanup. Rb15 increases the allocation to 256 words, guards every
Copper emission and records actual usage/capacity/overflow in `renderbench.log`.
Test rb15 before any production renderer migration. The accepted
3+3 game remains recoverable as commit `26b281a` on `main`.

Rb17 premium idle art proof
---------------------------

Rb17 retains the accepted rb16 display proof and replaces its automatically
recoloured production-sheet pose with one newly authored, broader 64x64
premium idle candidate. It uses the representative Storm Ruins
rear/foreground palette and places one static 15-colour bipedal Strider
idle at world x=286, y=146 before display takeover. It should scroll left with
the foreground while the rear remains at quarter speed. Look for coherent
indigo/violet/blue torso and limb modelling, cyan visor/conduits, stable edges
and clean Workbench restoration. This is an artistic colour-depth proof, not a
gameplay, animation or dynamic-Bob test. The log must identify
`2026-08-12-rb17-premium-aga15-strider-idle`, report
`strider_idle=aga15 loaded=1 size=64x64` and no Copper overflow.

Rb17a reserves one transparent row beneath the sprite. This removes the six
isolated bottom-row pixels seen in the user-supplied rb17 recording; they were
downsampling residue between the feet, not part of either foot or the tail.
Rb17b moves that cleaned pose one display pixel down so its last opaque row
again meets the ground instead of appearing to hover above it.
Rb17c removes three disconnected source clusters on row 62 beneath the two
otherwise continuous soles. Row 61 is now the deliberate final opaque row and
the pose moves to y=146 so that row, not the discarded fragments, meets ground.

Rb18 keeps that accepted silhouette/baseline and tests the final colour
direction: fewer near-duplicate blues, separate neutral-steel and violet armour
ramps, restrained cyan energy pens and one magenta warning pen. This remains a
single static art proof and does not begin the production renderer migration.

Run sparkpaw-renderbench from its directory. Click the left mouse button to
exit, or wait approximately one minute.

After a normal exit it writes renderbench.log beside the executable
(PROGDIR:). The log records the exact build, display/fetch values, frame
count, exit reason and Workbench restoration path. Please send this small
text file with any visual report.

This first isolated benchmark tests only the risky display foundation:

- a private PAL Copper display, independent from Intuition and Workbench;
- two independently hardware-scrolled 672x256 planar bitmaps;
- foreground at full speed and background at quarter speed;
- explicit 320x256 display/fetch timing and one update per PAL frame;
- no gameplay, sprites, HUD, full-screen copies or per-frame drawing.

Expected result: a full-height display with two differently scrolling layers.
The foreground automatically travels left/right. The background moves slower.

If it is malformed or half-height, photograph it and report whether it was
started from HD or ADF. If it is correct and smooth, the next benchmark adds
the tile-edge updater and an AGA hardware sprite.
